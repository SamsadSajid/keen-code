Auto approval: four design options

Source: Issue 96. Use a small approval subagent in the first release. Keep its input small. Examine risky file operations as well as shell commands.

Code map

The REPL owns the mode and permission requester. Tools call filesystem guards before they request permission. Bash uses a static command classifier. The LLM package provides provider clients. The general subagent runner can add tools and project context. The selected design uses a separate approval subagent to keep those inputs out.

A. Classify pending permission requests

Put a subagent behind the permission requester. Send the tool name, command or path, resolved path, and risk flag. Approve only a strict safe result. On other results, ask the user.

Benefit: Small change. Existing tool interfaces remain unchanged. Cost: Commands and reads that bypass the requester also bypass review. A path alone cannot show the effects of a file change.

B. Guard first, then review the exact operation

Add an optional operation review interface. Keep the existing permission interface. In auto mode, review Bash commands and file operations after the guard check. Use a fixed internal subagent with no tools, project instructions, history, memory, or skill catalog. Send bounded operation data. Do not truncate an operation into a different operation. Ask the user if the input is too large or the result is invalid.

Use local policy to require user review for sensitive paths, external paths, unknown tools, and MCP calls. For ordinary local reads, use the filesystem guard. For file changes, send bounded change data only when it contains no detected secret. Keep manual permission as the fallback. Do not store model grants as session grants.

Benefit: Covers risky operations without granting the subagent tool access. Cost: More tool integration and model calls. Secret detection is incomplete. A model decision is not a sandbox.

C. Review at the tool dispatcher

Wrap the registry and review every tool input before execution. Send a small typed operation to the subagent. Keep the tool guards as a second check.

Benefit: One common entry point. Cost: Direct tool calls and child registries need the same wrapper. Raw inputs can contain secrets. Path and edit semantics must be copied from each tool. A second permission request needs an exact operation grant.

D. Two subagents with a shared decision

Send the same bounded operation to two independent subagents. Approve only if both return safe. Ask the user on disagreement.

Benefit: A second review can find an error. Cost: Twice the model cost and more delay. The models can make the same error. This design does not remove the need for guards or operation data.

Common requirements

Add /auto and /mode auto. Keep plan, build, and yolo behavior. Auto mode must not weaken plan restrictions or hard filesystem denials. Use strict output parsing, an input limit, an output limit, a timeout, and cancellation. Unknown results require user approval. Test mode changes, tool integration, invalid output, secrets, paths, shell risks, cancellation, and provider errors. Do not cache grants in the first release.

Decision record

Three Terra review agents used medium effort. Each reviewed all four options. All three chose B. Read the security review, architecture review, and cost review.

The final design uses one isolated approval subagent. It keeps guards and manual fallback. It reviews eligible shell commands and file changes. Child tools use the same auto policy. MCP calls need manual approval. There is no decision cache. Read the architecture and trade-offs and the verification plan.
